# BUG-001: Quantity of 11 is accepted although the limit is 10

| Field | Value |
|---|---|
| Severity | Medium |
| Component | API / validation |
| Requirement | REQ-QTY-001 |
| Origin | **Seeded deliberately** (`ORDERDESK_DEFECTS=BUG-001`); not a defect in third-party software |
| Status | Fixed in the clean build; guarded by the tests below |

## Steps to reproduce
1. Start the application and reset the data.
2. `POST /api/orders` with `{"customer_email":"qa@example.com","items":[{"sku":"NB-A5","quantity":11}]}`.

## Expected
HTTP 422 `quantity for NB-A5 must be 1 to 10`.

## Actual
HTTP 201, order created for 11 units (total 132000 paise).

## Evidence
Captured by `scripts/capture_evidence.py` from a clean build and a defective build (`docs/bugs/evidence/BUG-001.json`):

```json
{
  "clean_build": {
    "step": "POST /api/orders NB-A5 x 11",
    "http_status": 422,
    "body": {
      "detail": "quantity for NB-A5 must be 1 to 10"
    }
  },
  "defective_build": {
    "step": "POST /api/orders NB-A5 x 11",
    "http_status": 201,
    "status": "PLACED",
    "subtotal_paise": 132000,
    "discount_paise": 0,
    "shipping_paise": 0,
    "total_paise": 132000
  }
}
```

## Root cause
`app/main.py` `create_order`: the upper bound becomes `MAX_QTY + 1` when the defect is on, an off-by-one in the limit.

## Fix and verification
Compare against `MAX_QTY`. Verified: the guarding test(s) fail with the defect on and pass on the clean build (see `reports/defect-matrix.md`).

Guarded by: `tests/api/test_pricing_boundaries.py::test_tc_qty_001_quantity_boundaries[11-422]` (boundary value 11).

## Why this test design catches it
Boundary value analysis: the valid range is 1..10, so 0 and 11 are the first invalid values on each side.
