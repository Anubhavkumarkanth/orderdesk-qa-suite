# BUG-006: E-mail without a domain dot is accepted

| Field | Value |
|---|---|
| Severity | Low |
| Component | API / validation |
| Requirement | REQ-VAL-001 |
| Origin | **Seeded deliberately** (`ORDERDESK_DEFECTS=BUG-006`); not a defect in third-party software |
| Status | Fixed in the clean build; guarded by the tests below |

## Steps to reproduce
1. Reset the data.
2. `POST /api/orders` with `customer_email` `user@nodot` and one valid line.

## Expected
HTTP 422 `invalid customer_email`.

## Actual
HTTP 201, order stored for `user@nodot`.

## Evidence
Captured by `scripts/capture_evidence.py` from a clean build and a defective build (`docs/bugs/evidence/BUG-006.json`):

```json
{
  "clean_build": {
    "step": "POST /api/orders with customer_email 'user@nodot'",
    "http_status": 422,
    "body": {
      "detail": "invalid customer_email"
    }
  },
  "defective_build": {
    "step": "POST /api/orders with customer_email 'user@nodot'",
    "http_status": 201,
    "status": "PLACED",
    "subtotal_paise": 12000,
    "discount_paise": 0,
    "shipping_paise": 4000,
    "total_paise": 16000
  }
}
```

## Root cause
`app/main.py`: the pattern used when the defect is on is `^[^@\s]+@[^@\s]+$`, which does not require a dot in the domain.

## Fix and verification
Use `^[^@\s]+@[^@\s]+\.[^@\s]+$`. Verified: the guarding test(s) fail with the defect on and pass on the clean build (see `reports/defect-matrix.md`).

Guarded by: `tests/api/test_orders_api.py::test_tc_val_001_invalid_email_is_rejected[user@nodot]`.

## Why this test design catches it
Equivalence partitioning of invalid e-mails: the other six invalid partitions were still rejected, so only this one slipped through.
