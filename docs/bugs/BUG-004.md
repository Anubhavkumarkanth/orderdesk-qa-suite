# BUG-004: Cancelling an order does not return stock

| Field | Value |
|---|---|
| Severity | High |
| Component | API / inventory |
| Requirement | REQ-LIF-002 |
| Origin | **Seeded deliberately** (`ORDERDESK_DEFECTS=BUG-004`); not a defect in third-party software |
| Status | Fixed in the clean build; guarded by the tests below |

## Steps to reproduce
1. Reset the data (NB-A5 stock is 50).
2. Place an order for 3 x `NB-A5`.
3. `POST /api/orders/{id}/cancel`.
4. `GET /api/products` and read NB-A5 stock.

## Expected
stock is 50 again.

## Actual
stock is 47: three units are lost from inventory on every cancellation.

## Evidence
Captured by `scripts/capture_evidence.py` from a clean build and a defective build (`docs/bugs/evidence/BUG-004.json`):

```json
{
  "clean_build": {
    "step": "place NB-A5 x 3, then cancel; read stock of NB-A5 (started at 50)",
    "stock_after_cancel": 50
  },
  "defective_build": {
    "step": "place NB-A5 x 3, then cancel; read stock of NB-A5 (started at 50)",
    "stock_after_cancel": 47
  }
}
```

## Root cause
`app/main.py` `transition`: the `UPDATE products SET stock = stock + ...` statement is skipped for `cancel`.

## Fix and verification
Restore the quantity of every order line when an order is cancelled. Verified: the guarding test(s) fail with the defect on and pass on the clean build (see `reports/defect-matrix.md`).

Guarded by: `test_tc_lif_004_*`, `test_tc_lif_005_*` (API), `tests/db/test_db_integrity.py::test_tc_dat_003_stock_is_conserved` (SQL), `tests/ui/test_checkout_ui.py::test_tc_ui_006_*` (browser).

## Why this test design catches it
Caught independently at three layers; the SQL conservation check (`stock + held units = initial stock`) needs no knowledge of the API.
